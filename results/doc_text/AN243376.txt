1 Introduction
Provisioning is the process of injecting authorized keys and policy configuration into a device. Original
equipment manufacturers (OEMs) use the provisioning process to load OEM root of trust (RoT) keys and OEM
policies into the PSOC™ Control C3 (P/M) 6 device. The provisioning of OEM keys, certificates, and policies
transfers device ownership from Infineon to the OEM. 
PSOC™ Control C3 (P/M) 6 devices can be provisioned using Infineon's Edge Protect Tools package, which
creates and downloads a provisioning packet into the device. This provisioning packet includes a RAM
application that can perform the provisioning, along with input parameters for the RAM application, such as the
policy file and keys.
This document provides detailed information about the various types of certificates, policies, RAM application,
and downloadable module (DLM) packages, all of which are included in or generated by Edge Protect Tools.
This document is not a programming specification. Refer to AN238998 - PSOC™ Control C3 MCU programming
specification.
1.1 Provisioning overview
The provisioning process enables the OEM to configure several boots and debug related policy configurations.
As a primary step, the OEM is required to ‘own’ the device before making any changes to the Infineon default
policies on the device. To take ownership of the device, the OEM needs to generate its own keys and certificate,
and provision the device with these, as shown in Step 1 of Figure 1. This step can be performed whenever the
OEM needs to change the root of trust (RoT) keys on the device, even while the device is in the development
lifecycle stage (LCS). After the transfer of ownership is completed, the OEM must then use the OEM_ROT_KEY to
perform further provisioning of the device for the purpose of policy modification as shown in Step 2 of Figure 1.
There are no restrictions on the number of times the device can be provisioned in the development lifecycle
stage. Therefore, provisioning can be utilized to carry out the following operations on the device:
• Replace keys and certificates
• Replace the OEM policy file
The device can then be provisioned 'one' time to transition into the production lifecycle by using the
production certificate. After the device is moved into the production lifecycle stage, it cannot be returned to the
development LCS and the OEM_ROT_KEY can no longer be changed through provisioning. In the production
lifecycle stage (LCS), you only have a single opportunity to perform key revocation, which allows you to replace
the existing OEM ROT keys with new ones. This operation is irreversible and can only be performed once.

1.2 Re-provisioning
In the production LCS, re-provisioning can be performed any number of times as long as the prov_oem_complete
flag is set to "false" in the OEM provisioning policy (/policy/policy_oem_provisioning.json). Once the
prov_oem_complete is set to "true" , the contents in SFlash are locked and no further provisioning is possible
(Refer to section Finalizing OEM assets). Note that this behavior applies to both the Development and
Production lifecycle stages.

2 Certificates
A digital certificate or a public-key certificate can be used by any entity to establish the ownership of a public
key. Certificates contain a public key, information about the public key, identity of its owner, and the signature
of the certificate authority (CA) that verifies the content of the certificate. A certificate signing request (CSR) is a
request sent from the entity that owns the public key to the certificate authority to verify the information
provided in the CSR and generate the certificate.
There are different kinds of certificates and CSR that are used in the context of PSOC™ Control C3x6 devices.
Certificate Purpose
OEM certificate This contains the OEM_ROT_PUBLIC_KEY, which is signed by the Infineon CA and
provisioned by the OEM to transfer the ownership of the device. See OEM certificate
OEM CSR This is a self-signed certificate signing request sent from the OEM to the Infineon CA to
generate the OEM certificate. See OEM CSR
For PSOC™ Control C3x6 devices, the certificates use the CBOR/COSE format. The device ownership is
transferred to the OEM when the device is provisioned with the OEM certificate. This certificate is signed by
Infineon through Edge Protect Signing Service (EPSS) and is verified by the device after provisioning. This
process ensures that only Infineon approved OEM certificate can be provisioned on the device. OEM certificate
contains the OEM root of trust public Key. The OEM root of trust private key must be protected by the OEM and
used during provisioning of the device to sign the OEM policy, and also to sign the user application images
before programming, in case secure boot is enabled.
2.1 OEM certificate
The OEM certificate contains the OEM_ROT_PUBLIC_KEY and enables the OEM to take ownership of the device.
This certificate must be signed by the IFX_ROT_KEY, and generated by Infineon's Edge Protect Signing Service
(EPSS) based on the CSR uploaded by the OEM. For more detailed instructions on generating the OEM CSR and
OEM certificate, see AN243370 – Getting started with PSOC™ Control C3 (P/M) 6 security.
The OEM certificate can be of two types:
• Development certificate: The development OEM certificate contains the OEM_DEV_PUBLIC_KEY that is
used by the OEM during the development LCS of the device. In the development lifecycle, the device can be
provisioned multiple times to change the policy/keys, and can also be restored to Infineon default policy
settings. When the development certificate is used, the keys are stored in a mutable memory and the
lifecycle of the device remains unchanged. Development OEM keys do not need to be secured and can be
replaced at any time by the OEM
• Production certificate: The production OEM certificate is used to transition the device from the
development to production LCS. This certificate must contain the production OEM_ROT_PUBLIC_KEY that
will be stored in the immutable memory region. Two sets of the OEM_ROT_KEYs are supported to enable
key revocation in the event of a security breach. The production OEM ROT keys, used for production
devices, must be securely stored and used by the OEM. These keys cannot be replaced by provisioning

3 Policy
The boot configuration of PSOC™ Control C3 (P/M) 6 devices is dictated by a policy file. All policy configurations
are applied during device boot up by the Infineon BootROM (ROM_BOOT + FLASH_BOOT). The policy file is a
JSON configuration file that defines the settings/configurations i.e., input parameters for device provisioning.
Refer to AN243370: Getting started with PSOC™ Control C3 (P/M) 6 security - Policy file for list of input
parameters that can be provisioned to device.
In the Infineon factory, the device is provisioned with a set of default policy configurations. This default policy is
packaged as a part of the Edge Protect Tools package and contains different sections that can be broadly
classified into the three OEM policy sections:
• Debug policy
• Boot policy
• DFU policy
The policy file also includes a Keys section where the user OEM_ROT_KEY and device parameters are defined.
The following figure shows what different input parameters are part of the policy file.

Once the Edge Protect Tools package is initialized on the host PC, see the JSON policy in the <application-
directory>/policy/policy_oem_provisioning.json file. This file can be edited using any text editor to customize
the policy.
The policy file is converted into a CBOR packet that contains all provisioning data by Edge Protect Tools. This
packet is then signed accordingly to the COSE format and the final packet is sent to the device during
provisioning by Edge Protect Tools. The RAM application on the device then receives the packet, verifies the
packet's signature, and processes the CBOR payload to get data for the provisioning. Typically, the RAM
application processes provisioning data to convert it to the asset format stored on the device.

3.1 Debug policy
The debug policy configuration is used by the OEM to control access to debug ports through two mechanisms:
• Direct configuration
- Enable/disable debug ports
- Infineon's default policy enables all debug configurations
• Authenticated debug
- Debug ports can be temporarily enabled using a debug token
- Token must be cryptographically signed with authorized OEM RoT keys
- Provides secure, controlled debug access when ports are disabled
Note: While Infineon's default policy enables all debug configurations, OEMs can implement authenticated
debug for enhanced security by requiring valid debug tokens to access disabled ports.
The authenticated debug works only when the debug field is set to “Permanently Disable” in the policy file.
When set to “Disable” , the debug ports are permanently disabled and cannot be enabled even with debug
token.

3.4 Key-revocation policy
When the PSOC™ Control C3x6 device transitions to the Production lifecycle stage, only a single key revocation
is permitted through the re-provisioning process. During ownership transfer, the OEM sends two OEM RoT keys
to the device — OEM_ROT_KEY_0 and OEM_ROT_KEY_1 — so that if one key is compromised, the other remains
available for OEM application validation.
By default, the BootROM uses OEM_ROT_KEY_0 as the primary key for OEM application validation, in both the
Development and Production LCS. If OEM_ROT_KEY_0 is compromised while in the Production LCS, the OEM can
re-provision the policy to revoke OEM_ROT_KEY_0 and designate OEM_ROT_KEY_1 as the primary key for BootROM-
based OEM application validation.
Key revocation is limited to the Production LCS and cannot be performed in the Development LCS. It is also a
one-time, irreversible process — once a key is revoked, the change is final, and no further revocation is possible.
To revoke the key, set its corresponding field value to true in the policy. The default policy configuration is
shown in the following code block:
Key-revocation policy default configurations
"key_revocation": {
      "revoke_oem_rot_key_0": {

3.6 Lifecycle stage (LCS) transitioning
The default LCS of the device out of factory is NORMAL_PROVISIONED. This is also called the development LCS.
To transition the device to the Production LCS, set the target_lcs parameter to SECURE in the device_policy
section of the policy_oem_provisioning.json file and provision the device.
"device_policy": {
  "target_lcs": {
    "description": "The LCS to which the transition should be done",
    "applicable_conf": "NORMAL_PROVISIONED, SECURE",
    "value": "SECURE"
  }
}
Note: The terms NORMAL_PROVISIONED LCS and DEVELOPMENT LCS are interchangeable; SECURE LCS is
equivalent to PRODUCTION LCS.
When transitioning the device to the Production LCS, it is recommended to set prov_oem_complete to true in the
OEM provisioning policy so that all assets in SFlash are locked against further modification (Refer to Finalizing
OEM assets). If the ability to re-provision the device during the Production LCS is still required, this field can
instead be left set to false.
Warning: Once the device is moved to Production LCS, it is permanently locked into this stage and cannot
be returned to Development LCS. The only further lifecycle transition available is to the Return
Merchandise Authorization (RMA) LCS. Once the device is moved to RMA LCS, it cannot be
returned to Production LCS nor Development LCS.

more. This tool is implemented in the Python programming language and uses several third-party Python

Edge Protect Tools package.

provisioning packets and communicates with the device using programming tools. It supports tools like
OpenOCD via the SWD interface or the DFU Host Tool via serial interfaces, such as I2C, SPI, or UART.

A DLM package is a structured binary file that contains:
• Infineon signed RAM_APP

5.1 RAM application (RAM_APP)
RAM applications are executable code loaded into the SRAM and executed in the PC0 (Protection Context 0)
(AN243370 – Getting started with PSOC™ Control C3 (P/M) 6 security). Certain device features, such as
provisioning and re-provisioning, are implemented using RAM applications. These applications are developed
by Infineon, signed with Infineon keys, and verified and launched by the device's BootROM. It is important to
note that RAM applications cannot be developed by OEMs.
RAM applications are packaged in the MCUboot image format. This format adds application metadata to verify
image integrity and authenticity, along with custom metadata in the tag-length-value (TLV) format.

5.4.1 Launch flow: BootROM DFU
Configuring the DFU Interface for Provisioning
EdgeProtectTools supports two interfaces for device provisioning:
• OpenOCD (default) — used for SWD-based communication
• Serial (DFU) — used for UART/I2C/SPI-based communication via the DFU protocol
To use the DFU interface instead of OpenOCD, complete the following two configuration steps before running
any provisioning command:
Step 1: Set the serial interface as the active tool
edgeprotecttools set-ocd -n serial -p <PATH_TO_DFUH_TOOL>
For example:
edgeprotecttools set-ocd -n serial -p C:\Users\xxxx\ModusToolbox\packs\ModusToolbox-Industrial-MCU-
Pack\tools\dfuh-tool
Step 2: Configure the serial port
Select the configuration command based on the protocol in use. Replace <id> with the MiniProg4 device ID (see
note below).
# UART configuration
$ edgeprotecttools serial-config --protocol uart --hwid MiniProg4-<id> --uart-baudrate 115200 --uart-
databits 8 --uart-paritytype None --uart-stopbits 1
# I2C configuration
$ edgeprotecttools serial-config --protocol i2c --hwid MiniProg4-<id> --i2c-address 12 --i2c-speed 400
# SPI configuration
$ edgeprotecttools serial-config --protocol spi --hwid MiniProg4-<id> --spi-clockspeed 1 --spi-mode 00
Note: Finding the MiniProg4 device ID: Run the following command to list connected devices and retrieve the
MiniProg4 <id>:
~/ModusToolbox/tools_3.3/fw-loader/bin/fw-loader.exe --device-list
For a full list of serial-config options and parameters, refer to the EdgeProtectTools documentation.
Once both steps are complete, use the standard provisioning commands as usual — no further configuration is
required. EdgeProtectTools will communicate with the device through the DFU protocol, and the BootROM will
handle the communication on the device side.
Example:
Provisioning the OEM policy over DFU:
edgeprotecttools -t psoc_c3x6 provision-device -p .\policy\policy_oem_provisioning.json
To enable DFU communication on the device, configure the DFU policy parameters as described in DFU policy.
For detailed information on the BootROM serial interface configuration, see the "BootROM serial interface"
section in the PSOC™ Control C3 (P/M) 6 MCU architecture reference manual.

A.3 CBOR and COSE format
The Concise Binary Object Representation (CBOR) is a data format used in PSOC™ Control devices for concise
data representation. The CBOR data format is defined as an Internet standard by RFC 8949, while the CBOR
Object Signing and Encryption (COSE) format is defined in RFC 8152. COSE is used to ensure authentication,
integrity, and confidentiality of exchanged data. Based on the JSON data model, the CBOR/COSE format is used
to transport binary data such as certificates, firmware images, policy files, etc. by the Edge Protect Tools.
Additionally, the CBOR web token (CWT), an open industry standard defined in RFC 8392 is used for wrapping a
CBOR packet. For example, policy files are represented in JSON format. During the creation of a provisioning
packet, the Edge Protect Tools converts the policy to CBOR, then wrap the payload to CWT for use as RAM
application input parameters. When a COSE object is used, the optional parameter 'cose-type' can be used to
identify the embedded object. The value to use with the parameter for each of the structures is defined in Table
9.
Table 9 CBOR tag and cose-type
CBOR tag cose-type Data item Semantics
98 cose-sign COSE-Sign COSE Signed data object
18 cose-sign1 COSE_Sign1 COSE Single signer data object
96 cose-encrypt COSE_Encrypt COSE Encrypted data object
16 cose-encrypt0 COSE_Encrypt0 COSE Single recipient encrypted data
object
97 cose-mac COSE_Mac COSE Mac data object
17 cose-mac0 COSE_Mac0 COSE Mac without recipient object
Edge Protect Tools can be used for conversion from CBOR to JSON format to create COSE_Sign and COSE_Sign1
messages, and to verify a COSE_Sign message. See Appendix A.2.
